**TL;DR:** Retrieval-Augmented Generation (RAG) selects evidence for each query.
Cache-Augmented Generation (CAG), as used here, processes a bounded shared
corpus once and reuses its key-value cache across queries. RAG scales to larger
or changing collections; CAG can reduce repeated prefix processing for small,
stable corpora. Neither guarantees grounded answers.

<!--more-->

## Introduction

An LLM's parameters do not provide a reliable, current or inspectable knowledge
source for every question. Applications often supply external evidence at
inference time when information is recent, proprietary or must be cited. RAG and
CAG are two possible patterns, not the only augmentation techniques. This
comparison is prompted by an
[IBM Technology video on RAG and CAG](https://www.youtube.com/watch?v=HdafI0t3sEY).

## Understanding RAG and CAG

### Retrieval Augmented Generation (RAG)

RAG operates through a two-phase system:

1. **Offline preparation**
   - Split documents into useful retrieval units.
   - Build an index using embeddings, keywords or both.
   - Store the source text and enough metadata to support filtering and
     citations.
2. **Online query and response**
   - Retrieve candidates relevant to the query.
   - Optionally filter, rerank or diversify those candidates.
   - Place the selected evidence and the query in the model's context.
   - Generate an answer grounded in the retrieved evidence.

For example, if asked _"What film won Best Picture this year?"_, the system
might retrieve information about _"Anora"_ winning the award, even if this
occurred after the model's original training.

A key advantage of RAG is its modularity - components like the vector database,
embedding model, or LLM can be swapped independently without rebuilding the
entire system.

### Cache Augmented Generation (CAG)

CAG takes a fundamentally different approach:

- Instead of retrieving knowledge for every query, CAG places a bounded corpus
  in the model's context.
- The model processes the reusable prefix and stores its attention state in a
  key-value (KV) cache.
- A later query reuses that cache, avoiding repeated processing of the shared
  prefix.
- The corpus must fit within the model's practical context limit, including room
  for the query and response.

The practical distinction is that RAG selects a subset for each query, while
this form of CAG processes one bounded shared prefix and reuses its attention
state.

## Comparing Capabilities

### Accuracy

- **RAG**: Accuracy depends heavily on retrieval. If the system fails to fetch
  relevant evidence, the model cannot use it.
- **CAG**: Makes the whole bounded corpus available, but the model may still
  overlook or misinterpret information in a long context.

### Latency

- **RAG**: Adds retrieval and reranking latency, but sends a smaller evidence
  set to the model.
- **CAG**: Can reduce repeat-query latency once the shared prefix is cached,
  although creating and retaining a large cache has its own cost.

### Scalability

- **RAG**: Can index large collections because only a selected subset is passed
  to the model for each query.
- **CAG**: Is bounded by the model's usable context and the memory required for
  the KV cache.

### Data Freshness

- **RAG**: Supports incremental updates to the index and source collection.
- **CAG**: Requires the affected prefix cache to be rebuilt when its source
  material changes.

## When to Use Each Approach

The video presents several scenarios to illustrate when each approach is more
appropriate:

1. **A static help manual**: CAG may be attractive if the relevant material fits
   comfortably in context and receives many queries.
2. **A large, frequently updated legal collection**: RAG is a better starting
   point because it supports incremental updates and source-level citations.
3. **Clinical decision support**: A carefully evaluated hybrid may retrieve
   patient-specific and current evidence, then reuse that bounded context for
   follow-up questions. This remains a high-stakes application requiring expert
   review and controls beyond either retrieval pattern.

## Conclusion

Consider RAG for large or frequently updated sources, access-controlled
collections and systems that need source-level citations. Benchmark CAG when a
stable corpus fits comfortably within the usable context, many queries share it
and repeated prefix processing dominates latency. Compare answer quality,
citation fidelity, latency, memory and update cost on representative queries. A
hybrid or a simpler direct prompt may outperform either label.
