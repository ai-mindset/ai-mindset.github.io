**TL;DR:** Deno gives me one TypeScript toolchain for scripts, services, browser
code, data processing and some AI applications. Built-in formatting, linting,
testing and cross-compilation reduce friction, while npm compatibility fills
many library gaps. It is my preferred way to move away from Python, not a claim
that the TypeScript ecosystem has parity with Python for every scientific
workload.

**Update: August 2026 - After trialling Go, Rust, Zig and Elixir, I settled on
Deno with TypeScript as my monolingual setup for AI Engineering and Data
Science. The decision is based on the workflows I actually use, with library
coverage evaluated task by task.**

<!--more-->

## Introduction

Python dominates data science and machine learning, but its environment and
deployment workflows have often interrupted my work. I have already described
[my attempt to simplify Python's tooling](/posts/bring-it-back-to-basics.html).
Deno became compelling because it lets me use TypeScript across more of a system
with one integrated command-line tool.

The key factors driving change are:

- Python environment management complexity
- Production security requirements
- Deployment workflow friction
- Need for type safety in large-scale AI applications

## The Deno Advantage and Ecosystem

### Core Capabilities

Deno provides useful defaults with:

- Native TS support
- Explicit runtime permissions for filesystem, network and subprocess access
- Cross-compilation through `deno compile`
- Built-in development tools

As Ryan Dahl emphasised in a
[Syntax podcast episode](https://www.youtube.com/watch?v=tZBCq8Ijkgw), Deno
works well for single-file scripts with direct imports. This aligns with work by
[Answer.AI](https://www.answer.ai/)'s
[Alexis Gallagher](https://www.alexisgallagher.com/) on
[single-script Python development](https://www.youtube.com/watch?v=t6-Uup-Alfs).

### AI and Data Processing Tools

The JavaScript and TypeScript ecosystem provides useful options, although these
are not one-for-one replacements for Python's mature scientific stack:

Data processing:

- [nodejs-polars](https://pola-rs.github.io/nodejs-polars/) for high-performance
  DataFrame operations
- [Observable Plot](https://observablehq.com/plot/) for visualisation

Machine learning and AI:

- [Transformers.js](https://huggingface.co/docs/transformers.js/index) for
  running pretrained models
- [TensorFlow.js](https://www.tensorflow.org/js) for machine-learning workloads
- [LangChain.js](https://js.langchain.com/) and
  [LlamaIndex.TS](https://ts.llamaindex.ai/) for LLM applications

Infrastructure:

- [Qdrant JS](https://github.com/qdrant/qdrant-js) for vector storage
- [Postgres and MongoDB clients](https://docs.deno.com/examples/connecting_to_databases_tutorial/)
  through npm and JSR packages
- [stdlib](https://stdlib.io/docs/api/latest) for numerical and scientific
  functions
- [NLP.js](https://github.com/axa-group/nlp.js/) and
  [compromise](https://github.com/spencermountain/compromise) for
  natural-language processing

## A Pragmatic Decision Framework

Modern AI systems need a short experimental feedback loop and an explicit path
to operation. Through experimentation, I found that a TypeScript-based approach
using Deno covers both for many of my projects.

### Production-First Design

Deno can run a small TypeScript file directly, then use the same formatter,
linter and test runner as a project grows. Its permission model limits ambient
access when permissions are scoped correctly; it does not make an application
secure by itself. `deno compile` can create target-specific executables, but
native dependencies and included assets still require testing. Within those
limits, simple TypeScript[^1] has covered most of my computational needs
productively.

### Practical Implementation Guide

A transition can start with a self-contained script or service rather than a
rewrite. I use libraries only where they remove work: nodejs-polars for suitable
tabular processing, Observable Plot for visualisation, and direct model APIs or
a framework for LLM applications according to complexity. Architecture and
deployment should follow the problem rather than the choice of runtime.

### Development Best Practices

[Iterative refinement](/posts/iterative-refinement.html) remains important.
TypeScript can catch useful interface mistakes before runtime, while tests and
boundary validation cover claims the type system cannot prove. Async operations
can keep I/O-heavy programs responsive when concurrency and error handling are
designed deliberately.

## Conclusion

Deno with TypeScript addresses several pain points I encountered in Python:
overlapping project tools, web-service boundaries and distributing small
utilities. The choice also carries costs, particularly when a task depends on
Python-only research code or deeply mature numerical libraries.

For my current work, the balance favours Deno. I can use one language from data
ingestion and analysis through APIs and browser interfaces, then package
supported applications without installing a separate runtime. That is a
personal, revisable engineering decision grounded in my workload rather than a
universal language ranking.
