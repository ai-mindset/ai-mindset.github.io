# AI Mindset agent guide

Just-in-Time Learning is a public, client-only knowledge site for essays and
curated resources about AI engineering, data, tools, and ways of working.

- Primary users: readers of the published site and maintainers adding content
  or evolving its small static-site toolchain.
- Stage and deployment: a live static site deployed from `main` to GitHub Pages
  by `.github/workflows/pages.yml`.
- Primary documentation: `README.md`; task definitions and dependencies:
  `package.json`; compiler configuration: `tsconfig.json` and
  `tsconfig.js.json`.
- Work tracking: no repository task ledger or issue workflow is configured.
  Follow the current request and use GitHub pull requests when collaboration is
  needed.

## Repository map

| Area              | Purpose                                                                    | Technology                                    | Path                          |
| ----------------- | -------------------------------------------------------------------------- | --------------------------------------------- | ----------------------------- |
| Published content | Posts and standalone pages                                                 | Markdown with limited YAML-style front matter | `content/`                    |
| Site source       | Static shell, templates, styles, images, and browser behavior              | HTML, CSS, JavaScript, TypeScript             | `site/`                       |
| Build tooling     | Content audit, generator, server, link checker, verifier, counter snapshot | Bun JavaScript/TypeScript                     | `scripts/`                    |
| Tests             | Generator, server, and visitor-counter tests                               | `bun:test`                                    | `tests/`                      |
| Counter inputs    | Release beacon and deploy-time count snapshot                              | Text and JSON                                 | `counter/`                    |
| Automation        | Build, daily counter snapshot, and Pages deployment                        | GitHub Actions                                | `.github/workflows/pages.yml` |
| Working research  | Provenance notes that are not published or build inputs                    | Markdown                                      | `research/`                   |

- `_site/` is generated by `bun run build` and ignored by Git. Never edit or
  commit it; change `content/`, `site/`, `counter/`, or the generator instead.
- `bun.lock` is committed dependency state. Let Bun update it when an approved
  dependency change requires that; do not hand-edit it.
- `node_modules/` and local agent configuration are ignored local state, not
  project source.
- There are currently no nested `AGENTS.md` files, tool-specific adapters,
  repository skills, or persistent task ledger. Keep this file as the canonical
  repository-wide policy unless a genuinely narrower area needs an override.

## Architecture and invariants

`scripts/build.js` recreates `_site/`, copies the static shell and images,
parses Markdown with `marked` plus `marked-footnote`, writes one HTML file per
post and standalone page, and emits `posts.json`. `site/script.js` fetches that
index in the browser and implements post rendering, search, tag and timeline
filters, theme selection, and the 404-page effects. `scripts/serve.js` is a
local allow-listed static server; production is GitHub Pages.

The visitor counter is intentionally approximate and backend-free. A browser
claims a versioned `localStorage` key before making one anonymous, no-cookie,
no-referrer request to a GitHub release asset. CI reads the asset's download
count into `counter/visitors.json`; the built site displays that snapshot.

Preserve these invariants:

- Source files are authoritative; generated `_site/` files are disposable.
- A post filename determines its public URL:
  `content/posts/YYYY-MM-DD-slug.md` becomes `/posts/slug.html`. Treat renames
  and slug changes as public-link changes and check compatibility first.
- The front-matter parser is deliberately not a full YAML parser. Use scalar
  values and flow lists such as `tags: [ai, deno]`; multiline flow lists are
  supported, block-list YAML and nested objects are not.
- Every published post has `layout: post`, a non-empty `title`, a `date` equal
  to the filename date, a non-empty `tags` flow list, a leading
  `**TL;DR:**`, and an `<!--more-->` excerpt marker. A `draft: true` post is
  omitted from the build but is still audited for the source conventions.
- Public files must agree across generation, local serving, browser references,
  and verification. When adding a root static file or directory, update the
  relevant `staticFiles`/page lists in `scripts/build.js`, `publicFiles` or
  `publicDirectories` in `scripts/serve.js`, and verification/tests where
  applicable. New standalone Markdown pages also need entries in
  `standalonePages` and the verifier.
- Keep the local server's path allow-list and traversal rejection intact. Keep
  scripts scoped to the documented content, source, generated, and network
  boundaries.
- Preserve counter privacy and uniqueness semantics: claim before sending, do
  not retry an uncertain beacon, send no credentials or referrer, validate
  snapshots, and keep totals non-negative. The release tag, asset name,
  storage-key version, workflow variables, and browser URL form one contract.
- The site has no application server, authentication, database, migrations, or
  production secret store. Do not introduce one implicitly for a static-site
  feature.

## Content and style

- Put posts in `content/posts/`, standalone published copy in `content/pages/`,
  and images in `site/images/`. `research/` is non-publishable working material;
  move or rewrite material into `content/` only when its own publication gate
  and the task's acceptance criteria are satisfied.
- Use root-relative internal links such as `/posts/deno.html` and
  `/images/Deno%202.png`. Do not add Jekyll `{% link %}` syntax, the site's own
  absolute GitHub Pages URL, or raw GitHub image URLs. `bun run verify` checks
  emitted internal targets and fragments.
- In prose outside fenced code, avoid em/en dashes, literal backslash-space,
  collapsed blockquotes, duplicate or unresolved footnotes, and unused
  footnotes. These are enforced by `scripts/audit-content.js`.
- Preserve the site's evidence-oriented editorial voice. Distinguish facts,
  estimates, personal views, case studies, and project synthesis; retain useful
  primary links and do not invent citations, quotes, dates, or measurements.
- Markdown source wrapping is not a rendered line break. Use Markdown's two
  trailing spaces only when a visible hard break is intended.
- Follow existing naming: JavaScript and TypeScript variables/functions use
  `camelCase`, TypeScript interfaces/types use `PascalCase`, and predicate names
  use forms such as `isVisitorSnapshot` where practical. Prefer existing domain
  terms: “post”, “standalone page”, “visitor snapshot”, and “approximate unique
  browser”.
- Preserve the existing vanilla UI and visual language rather than introducing
  a framework. Visible changes must work in light and dark themes and across the
  existing mobile breakpoint at 768 px.

## Toolchain and dependencies

- Bun is the only required development runtime. The exact version is pinned in
  `package.json` and read by the CI setup action.
- `package.json` is authoritative for scripts, dependencies, and the runtime
  pin. The TypeScript configurations define compiler libraries and checking
  scope.
- Production dependencies are limited to the pinned `marked` and
  `marked-footnote` npm imports. Prefer Bun/platform APIs and existing code.
  Ask before adding or replacing a production dependency, and preserve
  `bun.lock` when doing so.
- JavaScript is used for the generator, server, client UI, and most tests;
  TypeScript is used where the visitor-counter boundary benefits from explicit
  types. Keep both Bun type-check configurations clean instead of suppressing
  errors or weakening compiler settings.

## Commands and required checks

Run commands from the repository root. Install the locked dependencies with
`bun install --frozen-lockfile` before running project tasks.

| Purpose                                                       | Command                    | When to run                                                                                  |
| ------------------------------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------- |
| Format changed toolchain source                               | `bun run format`      | Before the full check for files in the configured formatting scope                           |
| Audit, format-check, lint, type-check                         | `bun run check`       | For every content or code change                                                             |
| Build and unit tests                                          | `bun run test`        | For every content or code change                                                             |
| Verify generated pages, links, metadata, and counter snapshot | `bun run verify`      | After `bun run test`                                                                         |
| Build only                                                    | `bun run build`       | When inspecting generated output without running tests                                       |
| Local development server                                      | `bun run dev`         | Manual browser verification; serves `127.0.0.1:8000` until stopped                           |
| Check external HTTP links                                     | `bun run check-links` | When adding or changing external URLs and network access is available; this is not a CI gate |

The required CI sequence is `bun run check`, `bun run test`, then
`bun run verify`. `test` builds first; `verify` expects that generated tree to
exist. Do not report a gate as passing if it was skipped or failed. External
link failures can be transient, so report the failed URLs and network context
rather than weakening the checker.

`bun run snapshot-counter` is an automation task, not a normal local gate. It
requires `VISITOR_DOWNLOAD_COUNT`, optionally accepts
`COUNTER_SNAPSHOT_DATE`, and rewrites `counter/visitors.json`. Do not fabricate
counts or run it against production data unless the request specifically calls
for counter maintenance.

## Testing and UI verification

- `tests/build_test.js` covers front matter, templates, legacy-link conversion,
  stable heading IDs, and Markdown line-break behavior.
- `tests/serve_test.js` covers the public-path allow-list, traversal defense,
  content types, and GET/HEAD file responses.
- `tests/visitor_counter_test.ts` covers one-time claims, failure behavior,
  snapshot validation, and count rendering.
- Add a focused regression test for behavior changes. Keep tests deterministic;
  inject storage, fetch, time, or DOM-shaped collaborators as the counter tests
  do instead of calling live services.
- There is no browser automation or screenshot suite. For relevant visual work,
  run the bounded gates and then inspect the home page, an affected post or
  standalone page, and any changed 404 behavior at desktop and mobile widths.
  Exercise search/filter interactions, keyboard-accessible controls, realistic
  long content, and both themes where the change reaches them.

## CI and external boundaries

`.github/workflows/pages.yml` runs on pushes to `main`, pull requests, manual
dispatch, and a daily schedule. On non-PR `main` runs it ensures the versioned
GitHub release beacon exists and snapshots its download count. The build job
then checks, tests, verifies, and uploads `_site/`; the deploy job publishes the
artifact for non-PR events.

- Do not push, deploy, publish a release, upload a release asset, or otherwise
  mutate GitHub or another external service unless the user explicitly asks.
- Do not print or commit `GH_TOKEN`, credentials, local environment values, or
  private data. The published site and counter snapshot are public.
- When changing GitHub Actions, preserve the PR boundary: pull requests validate
  without mutating releases or deploying Pages.
- Treat external content URLs and the GitHub release endpoint as untrusted or
  fallible. Keep validation, response checks, timeouts, and the counter's
  privacy options intact.

## Review and handoff

- Preserve unrelated and untracked user work. Inspect `git status` before and
  after editing, review the complete diff, and confirm only intended files
  changed.
- Keep changes small and source-based. Update documentation, tests, generated
  contracts, and allow-lists together when behavior crosses those boundaries.
- In the handoff, lead with blockers or required user action, then summarize
  behavior-level changes, commands run and their results, assumptions, and any
  remaining verification gap.
- Prefer commit subjects in the observed `<type>: <imperative summary>` style,
  using types such as `feat`, `fix`, `refactor`, `content`, or `chore`. Do not
  commit unless asked.

Keep this guide concise, durable, and repository-specific. Add a failure-log
rule only after a real recurring repository failure establishes a constraint
that is not already documented; do not record hypothetical failures.
